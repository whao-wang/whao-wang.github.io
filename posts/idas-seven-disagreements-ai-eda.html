把圆桌上的“非共识”展开后会发现，核心并不是谁对谁错，而是每个人站的位置不同：做模型的人看能力上限，做工具的人看产品形态，做签核的人看风险底线，做产业的人看真实需求和商业闭环。

一、AI 到底是“助手”，还是未来的设计主体？

CONSERVATIVE VIEWEDA 不像写代码，最终面对的是物理世界。版图、寄生、电迁移和工艺波动等问题，不能仅靠语言模型理解，更不能用“看起来合理”来判断。
AGGRESSIVE VIEW今天 AI 在 EDA 上不够强，主要受数据封闭和问题复杂度影响，而不是这件事原则上做不到。EDA 也可能沿着软件工程的路径快速演进。

按照相对保守的判断，AI 在短期乃至相当长一段时间内，更适合承担读日志、调参数、跑流程和生成候选方案等工作；人仍然负责关键判断，并对最终结果承担责任。

更激进的判断则认为，软件工程已经从“AI 只能辅助”逐渐走向“AI 承担主要工作量”，EDA 可能只是晚两到五年。再往后，AI 甚至不只是调用已有算法，还可能提出新的优化算法。

真正的分歧在于：AI 能力的上限在哪里，以及人何时会从“主要设计者”变成“监督者”？

二、要不要验证 AI 的中间过程？

一种思路是延续传统工程方法：AI 每走一步都要可解释、可检查。例如，在逻辑综合、布局布线和时序优化等关键节点，都设置明确的 checklist、风险等级和人工 review。好处是风险可控，尤其适合流片这种容错率极低的场景；代价是 AI 的自主性和效率会受到限制。

另一种思路更看重最终结果：不必要求 AI 像工程师一样思考，也不必要求每个中间决策都完全可解释。只要最终芯片通过全部签核并达到目标指标，即使中间过程与人类经验不同，也应允许它采用新的路径。

问题很尖锐：芯片设计能否像 AI coding 一样“结果正确即可”，还是必须做到“过程也可信”？

现实中大概率会按场景分层：越靠近流片和可靠性，越需要过程控制；越偏前期探索，越可以结果导向。

三、签核如何嵌入 AI 闭环？

大家都同意，最终必须使用高精度签核。但 AI 优化需要大量迭代：如果每次都跑全精度签核，速度和算力成本会难以承受；如果前期使用过于粗糙的近似模型，AI 又可能沿着错误方向持续优化，直到最终签核才发现方案不可用。

因此，现场真正没有答案的是一套可落地的“分层签核策略”：

  • 哪些指标可以先用近似模型，例如早期的功耗趋势、局部拥塞和粗粒度时序；
  • 哪些风险不能依赖近似模型，例如关键时序、EM/IR 和制造可靠性；
  • AI 每迭代多少轮，需要触发一次更高精度的验证；
  • 签核失败后，怎样把原因结构化地反馈给 AI，而不是只抛出一堆日志。
速度精度资源消耗

这本质上是一个三角约束：速度、精度和资源消耗无法同时最大化。

四、EDA 工具应该做 Agent，还是把自己做成更好的“工具”？

一种路线是“Agent 优先”：未来的工具不再主要面向工程师的 GUI 操作，而是提供细粒度接口、模块和插件，由 Agent 动态调用、组合和编排。传统工具链会逐步演变成一组可调用的专业能力。

另一种路线是“内核优先”：不要把主要精力都投入到一个看起来很聪明的 Agent 上。更有价值的方向，是用 AI 改造 EDA 内部的核心算法，例如发现更好的逻辑优化策略，再进一步重写确定性算法内核。这样产出的仍然是稳定、可复现、可验证的工具能力，而不是概率性的黑箱结果。

两条路线并不冲突，但资源投入的重点完全不同：

路线主要投资核心价值
Agent 优先接口、编排、上下文、工具调用提升全流程自动化和协同效率
内核优先算法、求解器、模型与传统引擎结合提升单点工具的确定性能力与上限

五、多 Agent 的难点到底是什么？

有人更关注架构问题：器件、电路、物理实现、签核、封装和系统设计之间，数据如何传递，约束如何下传，结果如何回传，不同 Agent 又如何协调目标。

但也有人认为，架构只是“把人连起来”。真正困难的是每个 Agent 是否拥有足够深的专业能力，也就是 Skill。没有工艺规则、设计经验、故障案例和优化策略，即使把再多 Agent 连起来，也只是多个“懂一点通用知识的助手”在协作。

例如，一个封装 Agent 是否理解热、应力、互连和良率之间的取舍？一个签核 Agent 发现 EM/IR 问题后，是否知道应该怎样修改设计？这些能力不来自多 Agent 框架，而来自长期的行业积累。

分歧可以概括为：先搭建多 Agent 平台，还是先沉淀真正能解决问题的专业 Skill？

六、数据与 Skill 如何进入系统，同时不泄密？

这可能是最现实的一条非共识。

模型要做深，就必须看到真实数据：设计数据、工艺规则、仿真结果、签核报告、失败案例，以及设计公司和晶圆厂多年积累的优化方法。但这些恰恰是产业中最核心、最不可能公开的资产。

MODEL-CENTRIC尽可能把行业知识、方法和数据纳入模型，以换取更强的泛化与自动优化能力。能力上限可能更高，但安全和知识产权风险也更大。
SYSTEM-CENTRIC不追求把知识全部“喂给模型”，而是让模型在受控环境中调用工具、规则库和私有 Skill，确保数据不外流。更适合产业落地，但系统复杂度更高。

七、3D IC 到底是机会，还是尚待验证的方向？

大家认可，3D IC 和先进封装会带来新的 EDA 需求，尤其是多 Die 协同、垂直互连、热、供电和物理实现问题。国产工具更容易围绕国内工艺、封装路线和客户流程进行深度适配，这确实可能形成国际工具短期覆盖不足的空档。

但另一种提醒是：不能因为 3D IC“看起来很热”，就直接把它等同于产品机会。过去不少 3D IC 方法和工具停留在研究阶段，原因并不是技术做不出来，而是缺少足够明确、规模化且愿意付费的客户需求。

现在的变化在于，先进制程继续推进的成本和难度不断上升，先进封装、Chiplet 和垂直堆叠开始进入更多真实产品。问题仍然是：这些需求能否持续，产业链能否协同，工具又能否真正进入客户的量产流程。

真正的分歧不是“3D IC 要不要做”，而是：它究竟是战略性投入方向，还是已经能够形成规模化收入的产品方向？
